ASX Reg Data

Documentation · v1.2.0

Overview

ASX Reg Data finds out which documents on an ASX rules / guidance-notes / waivers page were updated after a given cutoff date, and produces the evidence: sorted PDF folders, markdown reports and an Excel workbook.

1 · Scrape
Reads the page, finds every PDF link per tab (Rules, Guidance notes, Waivers, Appendices…).
2 · Download
Fetches all PDFs concurrently (6 workers) with cancel support and safe temp files.
3 · Analyse
Reads each PDF's internal date (modified, else created) and page count.
4 · Report
Updated / Not updated / No date / Error — folders, .md reports, report.xlsx.

Two front-ends, one core

  • Desktop app (gui_main.py, or the packaged ASX Reg Data.exe): New run, live Running view, Results dashboard, History, Date checker, Notes and the Agent placeholder; dark and light themes.
  • Command line (python main.py, python check_pdf_dates.py): same behaviour as before the GUI existed; only the "Project ID" prompt and summary wording became "DocumentId".

How a PDF is classified

StatusRule
UpdatedPDF date is after 00:00 on the cutoff day.
Not updatedPDF date is on or before the cutoff.
No date foundNo readable ModDate / CreationDate in the PDF (or the file is not a valid PDF).
Download errorThe file could not be downloaded.

The PDF date is the metadata modDate, falling back to creationDate. The upload date shown on the ASX page is read but is informational only.

Cutoff date guidance. If the cutoff date is unavailable or difficult to determine, derive it from the Waivers section: use the date of the most recent document in that section, which reflects the latest version delivered by CUBE.

Software Requirements Specification

Version 1.2.0 · structure follows IEEE 830 in a lightweight form.

1. Introduction

1.1 Purpose

Specify the behaviour of ASX Reg Data so that analysts, developers and QA share one definition of "done".

1.2 Scope

The product retrieves the PDFs published on an ASX regulation page, determines which changed after a cutoff date, and exports reports. It does not edit, convert or publish documents, and it does not talk to any system other than the ASX website.

1.3 Definitions

TermMeaning
Cutoff dateCalendar date entered by the user (YYYY-MM-DD). Documents dated after 00:00 of that day count as updated.
DocumentIdName of the output sub-folder for a run, e.g. AU--ASELA--REG--ASX-0. (Called "Project ID" before 1.2.0; the stored field is still project_id.)
StartpointOptional free-text label entered next to the DocumentId (for example a starting chapter or reference). Display-only: it does not influence folders, downloads or classification.
NoteA developer note: a heading plus text with bold, italic, underline and colour. Stored per user.
SectionA tab on the ASX page (Rules, Guidance notes, Waivers, Appendices…); also a sub-folder of downloads/.
RunOne execution of scrape → download → analyse → report for a DocumentId.
Run summaryrun_summary.json, the machine-readable result of a run (see Data & files).

2. Overall description

  • Users: CUBE analysts and developers of the ASX domain (non-programmers must be able to operate the exe).
  • Environment: Windows 11 x64 (the tested platform) or Windows 10 1809+ (the minimum for Qt 6), no administrator rights, internet access to www.asx.com.au (HTTPS).
  • Constraints: one run at a time; Windows' 260-character path limit applies; output folder must be writable.
  • Assumptions: PDFs carry usable metadata dates; the ASX page keeps its tab structure (a whole-page fallback exists).

5. External interfaces

  • User interface: desktop window (Qt), see User guide.
  • File system: reads/writes the output folder; logs in %LOCALAPPDATA%\ASX Reg Data\logs.
  • Network: HTTP(S) GET to the page URL you enter and to the PDF links on that page — normally all on www.asx.com.au. Nothing else is contacted.
  • Registry: per-user settings under HKCU\Software\CUBE\ASXPDFChecker (QSettings).

6. Acceptance criteria

  1. For any live page the GUI pipeline and the CLI report identical category counts (tools/parity_check.py). Reference result on 2026-10-23, ASX 24 page, cutoff 2024-01-01: 364 PDFs — 60 updated, 304 not updated, 0 no-date, 0 errors (the live page may change over time).
  2. All automated checks in Testing & QA pass, and the packaged exe passes --selftest, starts, and exits cleanly.
  3. Every day number (1–31) is readable in the calendar popup in both themes.

Design choices

  • Core is Qt-free. core/ (pipeline, summary, date check, paths) can be tested without a display and is shared conceptually with the CLI.
  • Hooks, not forks. The downloader and analyzer gained optional progress_cb / cancel parameters, the logger a pluggable handler list and the output-folder helper a root argument; the pipeline checks the cancel flag between stages. The CLI calls everything without these and behaves as before.
  • One render path. A live result and a History re-open both go through load_run().

Architecture

A thin Qt shell over a Qt-free core, sharing the original scraper / analyzer / reporter modules with the CLI.

Run lifecycle

  1. New run validates the form and emits a RunRequest; MainWindow shows the Running view and calls JobRunner.start_run.
  2. JobRunner moves a worker to a QThread; the worker calls run_pipeline(req, progress_cb, cancel).
  3. The pipeline scrapes, creates folders, downloads (thread pool), clears old copies, analyses, writes reports and the summary. Progress is throttled to ~20 updates/s; failed files are never throttled.
  4. Cancel sets a threading.Event directly from the GUI thread; downloads stop between chunks and temp files are removed.
  5. The result (RunResult) returns via a signal; completed runs open in Results, others stay on the Running view with the reason.

Output layout

output/
└─ <DocumentId>/
   ├─ downloads/<section>/*.pdf        every PDF, grouped by page tab
   ├─ Updated_Books/*.pdf              copies of PDFs dated after the cutoff
   ├─ Date_Not_Found/*.pdf             copies of PDFs with no usable date
   ├─ analysis_report.md               full inventory by category
   ├─ updated_page_count.md            pages of updated PDFs
   ├─ report.xlsx                      single sheet + summary panel
   ├─ run_summary.json                 latest run (GUI runs)
   ├─ history/run_<YYYYMMDD_HHMMSS>.json   one archive per run (feeds History)
   └─ date_checks/<cutoff>_<time>/    optional Date checker exports

Logs: %LOCALAPPDATA%\ASX Reg Data\logs\asx_checker.log (rotating) and crash.log for unexpected errors.

report.xlsx

  • One sheet, one table: Document ID, Section, Document Name, Date Modified/Created, Book Status, Page Count, Dev Status, QA Status.
  • Dev Status (Todo, Inprogress, In-review, Fixing) and QA Status (QA PASS, QA Fail, Reviewing) are dropdowns for analysts to fill in. The tool never writes values into them, but re-running a DocumentId regenerates report.xlsx from scratch — copy the workbook first if it already contains analyst entries.
  • A right-hand panel of formulas (totals, updated counts and pages, per-section breakdown, status breakdowns) recalculates from the table.

run_summary.json (schema v1)

{
  "schema_version": 1,
  "app_version": "1.2.0",
  "kind": "run",                       // or "date_check"
  "meta": {
    "run_id": "20261023_101500", "project_id": "...",   // the DocumentId
    "startpoint": "",                  // optional; absent in files written before 1.2.0

    "status": "completed",             // completed | cancelled | failed
    "error": null, "warnings": [], "source_run": null, "output_root": "..."
  },
  "stats": {
    "total": 364, "updated": 60, "not_updated": 304, "no_date": 0, "download_error": 0,
    "updated_pages": 0, "total_pages": 0,
    "by_section": { "Rules": { "updated": 0, "not_updated": 0, "no_date": 0, "download_error": 0 } }
  },
  "entries": [ { "name": "...", "url": "...", "section": "rules", "section_label": "Rules",
                 "upload_date": null, "http_date": null, "pdf_meta_date": "2025-06-01T12:00:00",
                 "resolved_date": "2025-06-01T12:00:00", "date_source": "pdf_metadata",
                 "local_path": "downloads/rules/x.pdf", "page_count": 12,
                 "download_error": "", "category": "updated" } ]
}
  • Dates are naive ISO-8601; local_path is relative to the project folder (absolute paths, drive letters and .. are rejected on load).
  • Files are written atomically (temp file + rename). A newer schema_version is refused with a clear message.
  • Fields added later (such as startpoint) are optional: older files still load and show an empty value.

notes.json (Notes)

Location: %LOCALAPPDATA%\ASX Reg Data\notes.json — one file per Windows user, not shared and not part of the app folder, so it survives updates.

{
  "schema_version": 1,
  "notes": [ { "id": "3f2a…", "title": "Release checklist",
               "body_html": "<p><b>Before shipping</b> …</p>",   // only p, br, b, i, u, span[color]
               "body_text": "Before shipping …",                          // plain text for search/preview
               "created_at": "2026-10-24T09:07:00", "updated_at": "2026-10-24T09:07:00" } ]
}
  • Limits: heading up to 120 characters, text up to 200 000 characters.
  • Writes are atomic and the previous version is kept as notes.json.bak.
  • An unreadable file is never overwritten: it is renamed notes.corrupt-<time>.json and a new list is started (the Notes page says so). If only some entries are damaged, the rest load and a copy of the original is kept as notes.damaged-<time>.json. A file written by a newer app version is refused and left untouched.
  • Saving is all-or-nothing: if the file cannot be written (locked, disk full), the list in memory is not changed, so nothing is lost or resurrected later.
  • The text is stored as plain JSON on disk: do not put secrets in notes.

User guide

1 · Start a run

  1. Open New run. Enter the DocumentId, optionally a Startpoint (free text; shown beside the DocumentId on the result, run, history and date-check screens), and paste the Page URL.
  2. Type the Cutoff date as YYYY-MM-DD (dashes are added for you) or pick it from the calendar button. The field is intentionally blank.
  3. Check the Output folder (use Browse… to change it; the choice is remembered).
  4. Press Start run. The button stays disabled until every field is valid; messages appear under fields you have visited.
Developer note. If the cutoff date is unavailable or difficult to determine, derive it from the Waivers section: use the date of the most recent document in that section, which reflects the latest version delivered by CUBE.

2 · Watch the run

The stepper shows Scrape → Folders → Download → Analyse → Reports. The panel shows counts, files per second and ETA; Live log expands the log. Cancel run stops the job; files already downloaded are kept, no reports are written.

3 · Read the results

  • KPI cards and the status donut show counts; click a card, slice or legend row to filter the table. Click again to clear.
  • Books per section: click a segment to filter by section and status.
  • Table: search (Ctrl+F), status chips, section list, click headers to sort, right-click a row for Open PDF, Show in folder, Copy URL; right-click the header to show the Date source and URL columns. Double-click opens the PDF.
  • The buttons above open the output folder, Updated_Books, Date_Not_Found, report.xlsx and the analysis report.

4 · History

Lists runs made with the app (newest first). Double-click or Open results re-opens a completed run; Remove from list hides it without deleting any file.

5 · Date checker

  1. Choose a project folder (or a downloads folder, or any folder of PDFs) — pick from earlier runs or browse.
  2. Enter a new cutoff date and press Check dates. Nothing is downloaded, copied or overwritten.
  3. Use Export reports to write the reports to date_checks/…. Use Close results (or Esc) to dismiss the result and return to the form.

6 · Notes

  1. Open Notes and press New note (Ctrl+N). Give it a heading and write the text.
  2. Select text and use B, I, U or the A colour menu. Those four are the only formats; pasted text is always plain.
  3. Save (Ctrl+S) stores the note. The status shows Unsaved changes until you do; if you switch notes, leave the page or close the app first, you are asked whether to save.
  4. Click a note in the list to open and edit it; the search box filters by heading and text. Delete asks for confirmation and cannot be undone.
  5. Notes are private to your Windows account (see Data & files); they are not shared with colleagues.

7 · Agent 🤖

A placeholder page: the Agent is under construction and coming soon. There is nothing to configure yet.

Build & release

powershell -ExecutionPolicy Bypass -File packaging\build.ps1

What the script does

  1. Reads the version from core/version.py (single source of truth; must be numeric MAJOR.FEATURE.FIX, e.g. 1.2.0).
  2. Creates .venv-build and installs requirements-gui.txt (pinned).
  3. Writes the Windows version resource and creates the icon if missing.
  4. Runs PyInstaller with packaging/asx_pdf_checker.spec: one-folder, windowed, no UPX, unused Qt modules excluded.
  5. Gate 1 — self-test: runs the exe with --selftest (imports, PDF round trip, scraper parse, reports and summary round trip, notes store and sanitizer, renders every page in both themes). A failure stops the build.
  6. Gate 2 — launch test: starts the exe, requires a main window after 8 s, closes it like a user, and requires exit code 0 and no growth of crash.log.
  7. Copies docs/ next to the exe and zips the staged folder to dist\ASX_Reg_Data_v<version>.zip. Older release zips are left alone.
  8. Publish: only after every gate has passed, dist\ASX Reg Data is refreshed from the verified build. The build itself happens in build\stage, so a running copy in dist is never disturbed: if the exe is running from dist, publishing is skipped with a message (the zip is still complete) and can be done later with build.ps1 -PublishOnly. A user's own dist\ASX Reg Data\output folder (where runs land when the exe is started from there) is moved aside while publishing and restored afterwards.

Versioning

Releases are numbered MAJOR.FEATURE.FIX — for example v1.2.0:

PartBump it forResetsExample
MAJOR (first)A major release: a large change in what the product is or how it is used.FEATURE and FIX → 01.4.2 → 2.0.0
FEATURE (second)A feature release: new capability, no major redesign.FIX → 01.2.3 → 1.3.0
FIX (third)A bug-fix release: corrections only, no new features.—1.2.0 → 1.2.1

History so far: 1.0.0 first GUI release → 1.1.0 feature release → 1.2.0 feature release (DocumentId/Startpoint, Notes, Agent). The rule is also written at the top of core/version.py; tools/docs_check.py fails the build when the version is not N.N.N or has no Changelog entry.

Releasing a new version

  1. Choose the next number with the rule above, set APP_VERSION in core/version.py, add an entry to the Changelog tab of this file and update the version in its header/footer (tools/docs_check.py fails the build if it is missing).
  2. Run the test scripts (Testing & QA), then build.ps1.
  3. Optional live check of the packaged exe: set ASX_SELFTEST_URL to an ASX page and run "ASX Reg Data.exe" --selftest; the log must report a scrape count.
  4. Hand over the zip. The exe is unsigned, so Windows SmartScreen may show "Run anyway".

Packaging notes

  • Windowed exes have no stdout/stderr; gui_main.py replaces them before anything else is imported and writes unhandled errors to crash.log.
  • Typical size: ~146 MB for the app folder, ~65 MB zip (anything a user's own runs add under output\ next to the exe is extra, and build.ps1 carries it over when it publishes).
  • Fallback if a future Python/Qt combination misbehaves: build in a Python 3.13 venv.

  • Open report.xlsx in Excel while re-running the same project: a warning, not a failure.

Review

Each release candidate also gets an independent code review whose findings are verified before fixing; the 1.0.0 review fixed, among others, a page-fade crash, a summary path-safety gap and a progress-throttle bug.

Security & privacy

  • Local only. The app only contacts the host(s) in the URLs you give it. No telemetry, accounts or update checks.
  • Path safety. run_summary.json files may be copied between machines, so stored file paths are accepted only when relative and inside the project folder (drive letters, rooted paths and .. are rejected in both slash styles).
  • Input hygiene. The DocumentId becomes a folder name and is validated (no separators, no reserved Windows names, length-limited).
  • TLS. Normal verification with the bundled CA store. If the page fetch fails with an SSL error (typical of TLS-inspecting corporate proxies) the scraper — and then the downloader — retry without verification and log a warning. Use only on trusted networks.
  • Downloaded files are opened only when the user double-clicks or chooses Open PDF; the tool never executes them.
  • Notes. Stored in plain JSON in your per-user application-data folder (not encrypted, not shared); do not keep secrets in them. Note text is reduced to bold / italic / underline / colour on save and on load, so pasted or hand-edited content cannot add fonts, links, images or scripts.
  • Crash handling. Unhandled exceptions are written to crash.log; no data is sent anywhere.
  • Unsigned build. Verify the zip's origin; SmartScreen warnings are expected until the exe is code-signed.

Known limitations

  • One job at a time (a run or a date check).
  • The page fetch cannot be interrupted once started (up to 60 s); cancel takes effect right after it. A download stalled on the network can take up to 30 s to stop after Cancel.
  • History lists only runs made with the GUI (older CLI runs have no run_summary.json).
  • Dev / QA status columns in the workbook are edited in Excel, not in the app.
